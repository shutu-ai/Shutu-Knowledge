# 0.4 Gap Analysis — Shutu 0.3 to Knowledge Internalization

Status: PH0 complete. Baseline audited: `v0.3.1` worktree at commit
`65573ff` plus the current unmodified 0.3 runtime code. This document compares
the real 0.3 implementation with the 0.4 objective, not with marketing feature
lists.

## Baseline evidence

* `docs/retrieval.md`: hybrid BM25/vector/RRF/rerank/MMR pipeline, structured
  filters, diagnostics, and token-bounded evidence windows.
* `docs/document_ir_design.md`: deterministic Document IR v1, typed nodes,
  page/slide/sheet/cell anchors, generation-scoped publication.
* `internal/documentir/document.go`: parser-independent node and structural
  relationship model.
* `internal/knowledge/understanding.go`: deterministic per-document outline,
  document/section summaries, and frequency-based key concepts.
* `internal/storage/migrations/0018_document_intelligence.sql`: additive
  `document_nodes`, `document_relationships`, `chunk_node_links`, and
  `derived_knowledge` tables.
* `internal/knowledge/benchmark_test.go`: deterministic local benchmark for
  retrieval quality and stage latency/allocations.

The existing `derived_knowledge` table is important but intentionally narrow:
records are per document and generation, expose an API by document, are not
searchable, are not canonicalized across documents, and do not model typed
semantic relations, temporal validity, contradictions, or topic hierarchy. It is
a migration foundation, not 0.4 Semantic Memory.

## Non-goals preserved from 0.3

* Do not retrain or edit model weights.
* Do not change the 0.3 evidence schema in a way that requires rebuilding it.
* Do not remove BM25/vector/RRF/rerank/MMR behavior.
* Do not require an external graph/vector/database service.
* Do not make compilation mandatory for opening or searching an existing KB.
* Do not reopen stable runtime, OCR, Office parsing, generation-isolation, or
  release-packaging issues.

## Migration constraints

1. Add new 0.4 tables and indexes; do not mutate existing 0.3 rows destructively.
2. Existing KBs remain searchable after migration even with zero compiled units.
3. Existing Document IR and chunks are sufficient provenance inputs; no Evidence
   Index rebuild may be required.
4. A compilation may be scheduled later; it must expose status and failures
   without blocking ingestion/search.
5. Deleting or replacing a document must invalidate all units derived from its
   generation and trigger only affected aggregate recompilation.
6. Existing `derived_knowledge` can remain for 0.3 compatibility; the 0.4 model
   should map or supersede it rather than silently reinterpret it.

## PH1 model implications

The first implementation phase must define:

* `KnowledgeUnit` identity, kind, canonical text, aliases, confidence, status,
  temporal fields, and base/document scope.
* `Provenance`: exact Document IR node IDs, chunk IDs, source anchors, document
  generation, compiler version, and model identity.
* `Relation`: typed subject/predicate/object, evidence provenance, confidence,
  validity, and deletion status.
* `Hierarchy`: child-unit membership used by Summary/Topic abstraction.
* `Versioning`: immutable compilation generation and atomic active-generation
  pointer.
* `Storage`: SQLite migration with searchable text, vector-ready projection,
  provenance indexes, and relation adjacency indexes.
* `Compatibility`: deterministic builtin compiler output and an optional LLM
  enrichment boundary that cannot claim facts without provenance.

## Success criterion

0.4 is not complete merely because these tables and APIs exist. It succeeds only
when the benchmark shows measurable improvement over 0.3 in global understanding,
cross-document association, multi-hop reasoning, knowledge reuse, or context
efficiency while fact retrieval, citations, migration, restart behavior, and 0.3
search quality remain sound.
