# 0.6 Historical Reasoning Gap Analysis

This analysis is based only on the committed 248-query run in
`benchmarks/real_world_internalization/temporal_results/latest.json` and the
published `docs/0.5_real_world_temporal_validation.md`.

## Why strict accuracy was 90.5%

The run had 14 strict temporal misses out of 148 queries. The only
range/history/ambiguous miss class was `AMBIGUOUS_TEMPORAL`: 8/8 cases failed.
The other misses were current selection (4), explicit version (1), and
introduced-in (1). Final LLM reasoning was not exercised because the benchmark
is an evidence-support proxy, so those misses cannot be attributed to answer
generation.

## Observed range/history failures

All eight ambiguous cases used this query:

```text
What happened in these earlier Open5GS release stages?
```

They represented successive slices of early Open5GS history, each expecting at
least one release post from the `v0.1.0 → v2.1.0` historical distribution. The
0.5 semantic path repeatedly returned `docs/_docs/guide/01-quickstart.md` and
`docs/_docs/guide/03-5g-eir.md`; it did not select any expected release-stage
evidence. Term coverage was 100%, but historical document selection was 0%.

| Failure | Example | Root cause | Layer | Proposed fix |
|---|---|---|---|---|
| Ambiguous temporal range collapsed to non-historical generic pages | Same “earlier Open5GS release stages” query with expected slices from v0.1.0 through v2.1.0 | Router has no ambiguous-history intent and no temporal range; retrieval follows generic words | Query router / context selection | Detect ambiguous history phrases and resolve a bounded corpus-derived range. |
| History represented as one top-K result set | The semantic context contains two generic pages rather than phase/release evidence | CompileContext has only exact-version narrowing and has no historical phase assembly | History context compiler | Assemble representative evidence by ordered version/phase rather than generic top-K. |
| “Earlier” was converted to implicit current-like search | No expected release posts appeared despite exact `release`/`Open5GS` terms | Ambiguity is not preserved as a historical range and has no phase boundary inference | Ambiguous intent | Add an explicit ambiguous-history route with confidence and open-ended boundaries. |
| Phase/transition evidence unavailable to context | Expected release-stage posts span multiple contiguous versions, but evidence has no phase grouping | Knowledge Units carry individual versions but no derived, provenance-backed phase projection | Historical phase model | Build temporary phases from explicit release/version distribution and include representative evidence per phase. |
| Relative boundaries are unsupported | “Earlier release stages” implies an open historical range ending before the current era, but cannot be expressed | Query model has exact versions and current resolution, but no start/end/inclusivity or open boundary | Temporal range model | Add separate version and time range types; keep ambiguous boundaries explicit. |

## Non-goals from observed data

The benchmark does not show a need for GraphRAG, a new graph database, ontology
reasoning, storage migration, memory consolidation, or a new parser. The failure
is localized to temporal range/history interpretation and context assembly.

## 0.6 design entry

The first implementation must reuse 0.5 VersionIdentity, temporal metadata,
supersession/conflict state, retrieval, and the context compiler. It should add
only:

1. `TemporalRange` with separate version/time semantics and open boundaries.
2. Ambiguous-history intent that preserves uncertainty.
3. Provenance-backed historical phases derived from ordered corpus evidence.
4. A budgeted history context compiler selecting representative evidence and
   evidence-backed transitions.
