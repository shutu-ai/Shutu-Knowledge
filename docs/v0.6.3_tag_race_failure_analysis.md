# v0.6.3 Tag CI failure analysis: cross-process historical reader

## Symptom

Immutable annotated tag `v0.6.3` points to `4699a697674020ce5e90b69523a764917cb8bf55`; its tag object is `5f4c3b21c1acd77dedd396a9c33434b9370eab48`. Tag CI run `35706624209` failed only `build → Test race` at:

```text
cross_process_historical_reader_test.go:165
cross-process reader pinned  chunks, want 20
```

The failed test itself took `24.98s`; the rest of the `internal/knowledge` package continued and completed in `820.896s`. No GitHub Release or artifact was published.

The exact failed-log line is important: the content between `pinned` and `chunks` was empty. The parent read a zero-byte marker file, not a partial SQLite generation or a GC-corrupted chunk view.

## Root cause

### Immediate CI failure: test synchronization bug

The child published its ready marker with:

```go
os.WriteFile(filepath.Join(workspace, "pinned"), []byte("20"), 0o600)
```

`os.WriteFile` first creates/truncates the destination and then writes bytes. The parent polled only for existence:

```go
waitForHistoricalReaderFile(t, filepath.Join(workspace, "pinned"))
pinnedCount, err := os.ReadFile(...)
```

Thus `READY` really meant “the pathname exists,” not “the historical reader established and acknowledged a complete pin.” On Linux, the failed CI run hit the create-before-write window and read zero bytes. This is deterministic from the protocol; it is not runner noise.

The marker is test-only coordination. It is not the production pin. The actual production pin is the child's long-lived SQLite WAL read transaction. The child first queries generation 1 and asserts a complete 20-chunk view before publishing the marker.

### Separate production correctness bug found in the required TOCTOU audit

The retired-generation GC code deleted chunks in bounded transactions first, then deleted the `document_generations` mapping later. For a large generation this left a legal window:

1. Old generation expires.
2. GC commits deletion of some/all old chunks.
3. Mapping still exists.
4. A newly started historical reader resolves the still-visible mapping.
5. The same request reads the already-partial chunk set.

This could violate the fail-closed historical evidence contract and the hard invariant that a reader which successfully establishes a complete pin must not see a generation disappearing underneath it. Existing readers that began before GC were safe: their WAL snapshot retained the complete old view. The defect concerned a new reader racing an already-expired GC.

The production fix retires the durable mapping before deleting chunks. After that atomic mapping deletion:

- a transaction that started earlier keeps its complete WAL snapshot; and
- every transaction that starts later fails closed with `ErrHistoricalEvidenceExpired`.

No obsolete generation becomes immortal; chunk deletion still proceeds immediately after the mapping fence.

## Test protocol timeline

Intended and now enforced sequence:

1. Parent builds generations 1 and 2 for 120 documents (2400 retired chunks).
2. Parent starts the child test binary with the database and target document.
3. Child opens a dedicated read DB and begins a read transaction.
4. Child queries 20 generation-1 chunks, establishing the WAL snapshot.
5. Child verifies the generation/source mapping.
6. Child writes full marker bytes to a temporary file, syncs, closes it, and atomically renames it to `pinned`.
7. Parent observes the final marker and independently reads `20`.
8. Parent expires generation-1 rows and invokes GC per document.
9. Parent publishes `gc-done`.
10. Child re-reads its original transaction and verifies unchanged mapping and 20 chunks.
11. Child commits, observes zero physical generation-1 rows, and publishes `reader-done`.
12. Parent waits for child success and verifies final GC counts/fail-closed access.

Before the fix, step 6 allowed the parent to observe an empty `pinned` file before any GC. The parent failed before triggering GC, so this CI failure did **not** demonstrate GC deleting required data.

## Invariant

> Once a historical reader has successfully established a complete WAL snapshot for generation G, GC must not mix, lose, or partially reclaim that reader's view until the reader releases it. Readers starting after G's durable mapping has been retired must fail closed; they must never resolve G and observe a partial chunk set.

The implementation uses SQLite WAL snapshots as the active-reader protection mechanism and the mapping lifecycle as the publication fence. There is no separate pin/lease table in this path. The bounded five-minute retired-generation grace exists for separately issued continuations; an already established transaction is protected by its snapshot.

## Changes

- `internal/knowledge/cross_process_historical_reader_test.go`
  - Publish `pinned` through a synced temporary file plus same-directory atomic rename.
  - Parent therefore observes complete marker content only after the child's snapshot and assertions are complete.
  - Make the failure diagnostic include the quoted bytes and byte length so zero-byte publication cannot be confused with a database count.
- `internal/knowledge/store.go`
  - Delete the expired `document_generations` mapping before deleting its chunks.
  - Establish the mapping as a fail-closed fence while bounded chunk transactions proceed.
- `internal/knowledge/generation_gc_order_test.go`
  - Add deterministic regression proving chunk deletion is rejected unless the generation mapping deletion fence was committed first.
  - Verify both physical objects are gone and separately issued historical access returns `ErrHistoricalEvidenceExpired`.

No storage schema, feature behavior, retrieval model, UI, or 0.7 work was changed.

## Runtime duration

The cross-process test consumed only `24.98s` under race instrumentation. The 820.896s number is the whole `internal/knowledge` package because Go continued other tests after the failure. On this local machine, a representative fixed race run spent roughly 15.9s in corpus build, 4.2s in GC, and 8.1s in the reader, for about 24.6s; race instrumentation dominates normal execution. This did not approach the workflow's 30m timeout.

## Validation and release decision

Classification: **BOTH**

- The tag failure itself is a **test synchronization bug**.
- The mandatory concurrency audit exposed a separate **production GC TOCTOU bug**, now fixed and regression-locked.

Because source changed, immutable `v0.6.3` cannot be repaired, retargeted, or reused. Decision: **CREATE v0.6.4 as a maintenance release**. This is “Generation GC / Cross-Process Historical Reader Correctness & Release Closure,” with no business feature expansion.

Required closure gates remain explicitly pending: full repository normal/race CI, web gates, browser E2E, formal package smoke, immutable `v0.6.4` tag CI, artifact/hash verification, and explicit publication approval. Do not publish a replacement under the failed `v0.6.3` tag.
